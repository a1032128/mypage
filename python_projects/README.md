# game-tracker

> 一個追蹤遊戲活動期限的爬蟲專案。每天自動把多個遊戲社群 wiki 的活動資訊整理寫入 Notion 資料庫，讓我不用每天一個個網站點開確認。

這份 repo 是我在 Python 課程結束後，把課堂上學到的靜態爬蟲（`requests` + `BeautifulSoup`）延伸做成的自由研究專案。課堂上老師沒有帶專題，所以我自己找了一個真實的生活需求當題目，從零開始把它做成一個每天自動執行的小系統。

## 動機

我平常會追蹤好幾個遊戲的活動，每個遊戲都有官方或玩家維護的 wiki 在更新活動清單。過去的做法是每天打開好幾個瀏覽器分頁一個個看，常常忘記、常常重複確認、常常漏掉已經快結束的活動。

課堂上學完爬蟲之後，我第一反應是「這不就是爬蟲最適合解決的事？」——資訊來源是公開的、格式化的、每天都在更新的網頁。如果能自動爬、自動存到一個我天天都會看的地方（Notion），這個問題就解決了。

這個題目對我來說有幾個好處：

1. **是我真的會用的東西**——不是為了交作業硬湊的題目，做完之後我每天都會受益
2. **難度剛好**——比課堂練習的單一網頁爬蟲複雜一點，但不到需要框架或深度學習那種程度
3. **可以一步一步擴展**——先把一個 wiki 爬通，再慢慢加其他來源

---

## 最終成果

- **8 個爬蟲**，對應不同的 wiki 平台（MediaWiki 系、wikiwiki.jp 系、swiki.jp 系、wikiru.jp 系、gamewith.jp 系、以及一個繁體中文的玩家 wiki）
- **一個 Notion 資料庫**，欄位包含活動名稱、遊戲、類型、開始日期、結束日期、狀態、來源網址、最後更新
- **Windows 工作排程器**每日自動執行，不需要手動觸發
- **失敗隔離機制**——任何一個爬蟲壞掉不影響其他爬蟲執行
- **完整 log 紀錄**，每次執行的結果會寫入 log 檔，出問題時可以查

每天早上八點，我的電腦會自己醒來，把最新的活動狀態同步到我的 Notion。打開 Notion 我就能看到「進行中」「即將開始」「已結束」的清單，不用再手動到處看。

## 技術棧

| 類別 | 工具 | 用途 |
|------|------|------|
| 語言 | Python 3 | 主要開發語言 |
| HTTP 請求 | `requests` | 抓網頁內容 |
| HTML 解析 | `BeautifulSoup` | 解析靜態頁面 |
| API 串接 | `notion-client` | 寫入 Notion 資料庫 |
| 機密管理 | `python-dotenv` | 把 token 跟 database ID 放在 `.env` 不 commit 到 git |
| 排程 | Windows 工作排程器 | 每日自動執行 |
| 日誌 | `logging` | 執行記錄 |

這些都是 Python 生態裡非常標準的套件，不依賴任何奇怪的東西。

## 系統架構

```
            ┌─────────────┐
            │  排程器     │  每天固定時間觸發
            │ (OS 層級)   │
            └──────┬──────┘
                   │
                   ▼
            ┌─────────────┐
            │  run.bat    │  啟動腳本，呼叫 python
            └──────┬──────┘
                   │
                   ▼
            ┌─────────────┐
            │  main.py    │  主流程：呼叫各爬蟲、整理、寫入
            └──────┬──────┘
                   │
       ┌───────────┴───────────┐
       ▼                       ▼
┌─────────────┐         ┌─────────────┐
│  scrapers/  │         │  Notion API │
│  *.py       │         │             │
│             │─────────▶             │
│  抓 wiki    │  結果   │  資料庫     │
└─────────────┘         └─────────────┘
```

每個 wiki 各自有一個 scraper 檔案，主程式（`main.py`）負責呼叫、統整，然後透過 Notion API 寫入資料庫。新增一個爬蟲只需要新增一個 scraper 檔 + 在 `main.py` 登記，其他部分不用動——這是我覺得這個架構最滿意的一點。

## 學習歷程

這個專案不是一次做好的。從什麼都沒有到現在的樣子，中間經歷了幾個明顯的階段：

### 第一階段：只有一個爬蟲

最開始只有一個 wiki，從頭到尾一條線。這個階段學到的：
- 怎麼觀察網頁的 HTML 結構、找到要抓的元素
- 怎麼處理不同格式的日期字串（有些有年份、有些沒有）
- 怎麼把 Notion 的 token 和 database ID 放到 `.env`，避免洩漏

### 第二階段：加第二個 wiki，發現問題

加第二個 wiki 的時候，我直接把第一個爬蟲複製貼上改一改。結果發現兩個問題：

- **兩個 wiki 的 HTML 結構完全不一樣**，所有解析邏輯都要重寫
- **`main.py` 變很亂**——所有 import 跟呼叫都寫在一起

這時候我重構了程式結構：把每個 wiki 獨立成一個 scraper 模組，`main.py` 只負責「按順序呼叫」。這是我第一次真實感受到「模組化」不是教科書裡抽象的概念，而是**當你要加第三個、第四個功能時救命的東西**。

### 第三階段：遇到 Cloudflare

某個 wiki 爬下去直接被擋，回傳的 HTML 是一個 Cloudflare 的驗證頁面。這讓我第一次接觸到「同一個網站可以有多個存取途徑」的概念——網頁瀏覽器看到的頁面被擋，但那個 wiki 的底層其實是 **MediaWiki**，而 MediaWiki 有公開的 API（`action=parse`），可以拿到乾淨的 HTML，而且**不會被 Cloudflare 擋**。

換一個存取途徑就通了。這個經驗給我的啟發是：**當你直覺上以為「這網站爬不了」的時候，常常只是你用錯方式。**

### 第四階段：加排程

到這邊為止，爬蟲都是手動執行的。為了讓它真正變成自動化，我研究了三種排程方式：OS 排程器、Python `schedule` 套件、GitHub Actions。最後選了 Windows 工作排程器，因為我的電腦本來就開著、不需要改程式碼、機密資料不用上傳到雲端。

排程這段遇到一個讓我卡很久的 bug（詳見下一節），那是整個專案裡最「挫折但學到最多」的時刻。

### 第五階段：防禦性設計

正式上線後的幾個微調，都是為了讓它在**我睡覺的時候自己處理問題**：

- 每個爬蟲用 `try/except` 包住，一個壞掉不影響其他
- Notion API 偶爾回 502，加三次重試機制
- log 記錄總筆數、成功、失敗數，一眼看完就知道昨天跑得怎麼樣
- `upsert` 邏輯：已存在就更新、不存在才新增，避免重複

這些是「看起來很雞毛蒜皮但實際上最重要」的細節。

## 踩過的坑

這一節記錄三個讓我印象最深、學到最多的錯誤。

### 坑 1：`PermissionError` 的真正原因不是權限

排程器設定好之後第一次跑，直接吐出 `PermissionError: Permission denied`。我花了很多時間在檢查檔案權限、看哪個程序佔著檔案、確認資料夾屬性——全都查不出問題。

後來才發現：**現代 Windows 會把「桌面」路徑重導向到 OneDrive**，而我的 OneDrive 桌面資料夾名稱是日文的「デスクトップ」。Python 在某種情況下試著去寫桌面，但它找到的路徑不存在，所以錯誤訊息字面上寫 `Permission denied`，實際上是**找不到路徑**。

這個經驗讓我學到：**錯誤訊息告訴你的是「工具以為發生了什麼」，不一定是「真正發生了什麼」。** 當修了三次都沒有進展時，該停下來重新檢查假設，而不是繼續修。

### 坑 2：排程器的工作目錄不是我以為的那個

解決桌面問題後還是出錯。明明手動跑 `run.bat` OK，但排程器跑就失敗。

查到最後發現：**工作排程器執行 `.bat` 的時候，工作目錄預設是 `C:\Windows\System32`，不是腳本所在的資料夾**。所以程式碼裡的相對路徑全部被解析到 System32 底下，而我當然沒有權限在那邊寫檔案。

解法是把所有路徑改成絕對路徑。Python 裡用 `os.path.abspath(__file__)` 可以拿到腳本的真實位置，不管誰從哪裡呼叫它都能正確運作。

這讓我體會到：**一份程式碼「會不會動」不只取決於程式本身，還取決於誰在什麼環境下呼叫它。**

### 坑 3：編碼問題

我的系統是繁體中文（CP950 編碼）。日文字在寫入 log 的時候有時會報 `UnicodeEncodeError`。解法是在 Python 的 `logging` 設定裡明確指定 `encoding="utf-8"`，並且用 `log.info()` 取代 `print()`，因為 `print` 會受終端機編碼影響，而 logging 可以自訂編碼。

這個問題原本我以為只會在輸出亂碼而已，後來發現它**會讓整個爬蟲 crash**，是個隱形的地雷。

## 反思

### 課堂學的 vs. 實戰需要的

課堂上教的是「給你一個網頁，抓出資料」。實戰上遇到的其實大部分不是抓資料本身——而是**這些周邊的事**：

- 資料抓到之後放哪？怎麼避免重複？
- 抓失敗怎麼辦？要不要重試？
- 程式要怎麼自己跑？排程怎麼設？
- 敏感資訊怎麼不外洩？`.env` 要怎麼用？
- 錯誤怎麼記錄？之後怎麼 debug？

這些單獨拎出來都是小東西，但加起來才是「一個能用的系統」跟「一段能跑的程式碼」的差別。課堂的練習讓我學會 `requests.get()`，但這個專案讓我學會**一個真正自動化的流程**長什麼樣子。

### 拆解問題的重要性

這個專案我是一個 wiki 一個 wiki 慢慢加的。如果一開始就想著「我要做一個支援 8 種 wiki 的爬蟲系統」，我會直接被嚇跑。但把它拆成「先做一個」「再多一個」「架構開始亂了，重構一次」「現在加第三個就容易了」——每一步都小、每一步都可完成、每一步都有進展。

### 最有用的心態

做完這個專案我體會最深的一件事是：**大多數時候卡關不是因為技術不夠，而是因為用錯角度在看問題。** Cloudflare 擋爬蟲、`PermissionError` 的桌面問題、排程器工作目錄的問題——每一個我卡住超過十分鐘的問題，回頭看都是「站在錯的地方找答案」。學會在挫折的時候停下來重新問「我現在的假設是什麼？哪裡可能錯了？」比任何特定的技術細節都更通用。

## 附錄：如何在本機跑這份專案

```bash
# 1. 安裝依賴
pip install requests beautifulsoup4 notion-client python-dotenv

# 2. 建立 .env（填入自己的 token 跟 database ID）
cp .env.example .env

# 3. 跑
python main.py
```

`.env` 需要兩個變數：
- `NOTION_TOKEN`：Notion integration 的 token（`ntn_` 開頭）
- `NOTION_DATABASE_ID`：目標資料庫的 ID（從網址列 `?v=` 前面那 32 個字元）

Notion 那邊還需要把 integration 分享給目標資料庫，否則會拿到 `object_not_found` 錯誤。

排程的設定請參考各 OS 的方式。Windows 是工作排程器、macOS/Linux 是 `cron` 或 `launchd`。
