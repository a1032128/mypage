01

為什麼做這個？

一個小麻煩，累積起來就變大了

我平常會追蹤好幾個遊戲的活動，每個遊戲都有玩家維護的社群 wiki 在更新活動時程。 過去的做法是每天打開好幾個瀏覽器分頁一個個看—— 常常忘記、常常重複確認、常常漏掉已經快結束的活動。

課堂上學完靜態爬蟲（requests + BeautifulSoup）之後， 我第一個念頭是：這不就是爬蟲最適合做的事嗎？

過去 / Before
  • 打開 6 個分頁
  • 一個一個點進去看
  • 常常忘記哪個快結束
  • 資訊散落在不同網站
  • 每天重複做一樣的事
→
現在 / After
  • 打開 Notion，一目瞭然
  • 活動狀態自動分類
  • 開始 / 進行 / 結束都清楚
  • 8 個來源統一整理
  • 每天電腦自己做

每天早上八點，我的電腦會自己醒過來，爬完所有來源、把資料寫進 Notion，然後靜靜地關閉視窗。 打開 Notion 我就能看到「進行中」「即將開始」「已結束」的完整清單， 不用再到處點開網站確認。

03

一步一步做出來的

這不是一次寫完的

這個專案最重要的一點：它不是一次做好的，而是一個階段一個階段長大的。 每個階段都解決了前一階段不知道存在的問題。

1

只有一個爬蟲

能跑起來就好

先挑一個 wiki，從頭到尾把「抓網頁 → 解析 → 寫進 Notion」這條線打通。

怎麼觀察 HTML 結構、怎麼處理不同格式的日期、怎麼用 .env 保護 token
2

加第二個 wiki，發現程式開始亂

複製貼上不是辦法

第二個 wiki 的 HTML 結構和第一個完全不同，所有解析邏輯都要重寫。主程式的 import 和呼叫全擠在一起，看起來很亂。

把每個 wiki 拆成獨立的 scraper 模組——這是我第一次真實感受到「模組化」不是抽象概念，而是當你要加第三個功能時救你的東西
3

遇到 Cloudflare，爬不到東西

以為走投無路的時候

某個 wiki 爬下去直接被 Cloudflare 擋，回來的 HTML 是驗證頁面。網路上的常見解法都試過沒用。

那個 wiki 底層是 MediaWiki，有公開的 API（action=parse）可以繞過瀏覽器路徑。很多時候「爬不了」不是真的爬不了，只是你用錯方式。
4

加排程，正式變自動化

讓電腦自己做

比較了三種排程方式（Windows 工作排程器 / Python schedule 套件 / GitHub Actions），最後選了 Windows 工作排程器。這一步遇到我整個專案最大的坑（下一節詳談）。

排程選擇的三個考量：電腦要不要一直開、要不要改程式碼、機密資料要不要上雲
5

加防禦性設計

讓它在我睡覺的時候也能處理問題

失敗隔離（一個爬蟲壞掉不影響其他）、Notion API 502 的自動重試、完整 log 記錄、upsert 避免重複寫入。

一個系統「能跑」和「能穩定地長期跑」中間還有一段距離，這段距離由很多雞毛蒜皮的細節組成
04

讓我卡最久的三個坑

老實記錄才有意義

做完之後回頭看，我卡最久的問題都不是「技術難度」的問題， 而是「用錯角度在看問題」的問題。

坑 1 · PermissionError 的真正原因不是權限

錯誤訊息會騙人
PermissionError: [Errno 13] Permission denied: 'game_tracker.log'

排程第一次跑就吐這個。我花了很多時間檢查檔案權限、看哪個程序佔著、確認資料夾屬性——全部沒問題。

後來才發現：現代 Windows 會把「桌面」資料夾自動重導向到 OneDrive， 而我的 OneDrive 桌面名稱是日文的「デスクトップ」。Python 在某個情況下試著寫到桌面， 但它找到的路徑不存在，錯誤訊息「碰巧」寫成了 Permission denied。

錯誤訊息只說明「工具以為發生了什麼」，不一定是真正發生了什麼。修了三次沒進展，該停下來質疑假設。

坑 2 · 排程器的工作目錄不是我以為的那個

同一份腳本，不同人叫它起來結果會不同

解決桌面問題後還是出錯。明明手動雙擊 run.bat 正常，但排程器跑就失敗。

真相：工作排程器執行 .bat 時工作目錄預設是 C:\Windows\System32， 不是腳本所在的資料夾。所有相對路徑全被解析到 System32 底下，而我當然沒有權限在那裡寫檔案。

LOG_PATH = os.path.join(os.path.dirname(os.path.abspath(__file__)), "log.txt")
程式碼「會不會動」不只取決於程式本身，還取決於誰在什麼環境下呼叫它。

坑 3 · 編碼問題讓整個爬蟲直接 crash

原以為只是亂碼，結果是地雷

繁中系統（CP950）碰到日文字，寫入 log 的時候直接 UnicodeEncodeError，爬蟲中斷。

解法：logging 設定明確指定 encoding="utf-8"，同時把所有 print() 換成 log.info()。

編碼問題不是「顯示不好看」，是「程式會 crash」。這類問題常常在開發環境看不到，上線才爆炸。
05

做完之後，最想寫下的一件事

如果只能帶走一句話

這個專案讓我學到的最重要的事，不是某個套件的用法，也不是某個錯誤的解法。 而是一種面對自己不會的東西的姿態：

大多數時候卡關不是因為技術不夠，
而是因為用錯角度在看問題。

Cloudflare 擋爬蟲、PermissionError 的桌面問題、排程器工作目錄—— 每一個我卡住超過十分鐘的問題，回頭看都是站在錯的地方找答案。 學會在挫折時停下來重新問「我現在的假設是什麼？哪裡可能錯了？」—— 這件事比任何技術細節都更長壽。

課堂教的是 requests.get()。這個專案教我的，是一個真正自動化的流程長什麼樣子—— 包括資料放哪、失敗怎麼辦、怎麼排程、敏感資訊怎麼管、錯誤怎麼記錄。 每一項單看都不難，加起來才是「一個能用的系統」跟「一段能跑的程式碼」的差別。

還沒做完的部分

誠實地說，這個專案不是完成品——有些爬蟲的 edge case 還沒處理、 Notion 的視覺呈現還能更好、有個遊戲官方根本不公告結束時間我還沒想到好辦法。 這也是這份作業的意義之一：它還在長大。
